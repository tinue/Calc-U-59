# Debug API Reference

> **Provenance notice.** This document was generated by an AI (Claude) from
> the source code. Like the other `reference/*.md` files it is best-effort
> and correct as of writing — the code wins where they disagree.

The debugger has three layers:

| Layer | Where | What |
|---|---|---|
| Core | `TI59Machine`, `TMC0501` (`Core/`) | RAM, program and SCOM access, the trace ring, step-boundary latch, debug events, the ASM overlay, breakpoints |
| Shared | `EmulatorSession`, `DebugModel`, `DebugSnapshots`, `DebugText`, `DebugLog`, `TraceWriter`, `AsmOverlay` (`Shared/`) | Freeze and step, the panels' data and text, the LOG, trace files |
| GUI | Swift: `EmulatorViewModel` → `Bridge/TISessionController`, views in `App/Views/` (`DebugView`, `LiveDebugView`, `CPUInspectorView`). Qt: `EmulatorController`, widgets in `Qt6/app/debug/` (`DebugPanel`, `LiveDebugWidget`, `CpuInspectorWidget`, `RomHeatmapWidget`, `AsmOverlayBox`, `LogWidget`) | Drawing only |

Both apps call the same `SessionController` methods; the panels draw what
`DebugModel` holds. Which panel lives where: `FrontendParity.md`
§ "Debugger". The session and controller: `SharedArchitecture.md`. Panel
behaviour from a user's point of view: the user guide,
https://www.calcu59.ch.

## Calculator-level machine access

`TI59Machine` calls the debugger and the state loader use. Writes are made
with the run loop stopped (`EmulatorSession::sync`), as
`Shared/StateApplier.cpp` does.

| Call | Effect |
|---|---|
| `copyRAMReg(reg, out16)` / `writeRAMReg(reg, n16)` | A raw 16-nibble RAM register by **physical** index (0 … `ramRegCount()` − 1) |
| `readProgramStep(step)` / `writeProgram(keycodes, count)` | Program keycodes from step 0 |
| `writeDataRegister(nn, n16)` | Data register Rnn (encode with `cu59::encodeBcd`, `Shared/Bcd.hpp`) |
| `decodeBCD(n16)` | A register as `double` |
| `partitionProgramRegs()` / `setPartitionProgramRegs(n)` | RAM registers given to the program, a multiple of 10 in [0, 120] |
| `snapshotCPU()` | A `CpuFrame` of the CPU now; safe while running. Its identity fields are not meaningful |
| `lastStepBoundary()` | The CPU state latched at the last step boundary or idle entry (see below) |
| `printerBufferContent()` | Characters in the printer accumulator not yet printed |

Helpers in `Shared/DebugSnapshots.hpp`: `programSteps(m)` (the partition's
steps, clamped to physical RAM), `romKeycodes(m)` (the 384 constant-ROM
keycodes), `decodeProgramCounter(cpu)`.

RAM layout, step nibbles and BCD register format: `CoreArchitecture.md`
§ "User RAM (TMC0598)" and § "BCD data registers".

**Partition.** `n Op 17` gives `(12 − n) × 10` program registers,
`(12 − n) × 80` steps and `n × 10` data registers. `setPartitionProgramRegs`
writes what the ROM's Op 17 writes, with no key simulation:

| SCOM nibble | Value (`p` = program registers / 10) |
|---|---|
| SCOM[9][0] | `p` |
| SCOM[13][8] | `p % 10` |
| SCOM[13][9] | `p / 10` |

## Freeze / Step Controls

The freeze state lives in `EmulatorSession`; `SessionController` mirrors it
and rebuilds the panels (`DebugModel`).

| `SessionController` | Swift `EmulatorViewModel` | Qt `EmulatorController` |
|---|---|---|
| `freeze(owner)` | `freeze(from:)` | `freeze(owner)` |
| `resume()` | `unfreeze()` | `unfreeze()` |
| `armPcChange()` / `disarmPcChange()` | `freezeOnNextPCChange()` / `pendingFreezeOnPCChange = false` | `freezeOnNextPCChange()` / `disarmPcChangeFreeze()` |
| `armScanLoopExit()` / `disarmScanLoopExit()` | `freezeOnScanLoopExit()` / `disarmCPUScanLoopFreeze()` | `freezeOnScanLoopExit()` / `disarmScanLoopFreeze()` |
| `stepKeycode()` | `stepKeycode()` | `stepKeycode()` |
| `stepInstruction()` | `stepFrozen()` | `stepFrozen()` |
| `setLiveDebugEnabled` / `setCpuDebugEnabled` | `liveDebugEnabled` / `cpuDebugEnabled` | `setLiveDebugEnabled` / `setCpuDebugEnabled` |

### `DebugState` (`EmulatorSession::debugState()`)

| Field | Meaning |
|---|---|
| `frozen` | Emulation is halted |
| `owner` | `FreezeOwner::Cpu` or `::Calculator`: the panel whose RESUME and STEP apply; empty while running |
| `pcChangeArmed` | CALCULATOR FREEZE ON START: freeze at the next step boundary |
| `scanLoopExitArmed` | CPU FREEZE ON START: freeze when the CPU leaves the keyboard scan loop (key press or reset) |
| `generation` | Changes on every freeze, resume and clear |

Arming one freeze disarms the other; freezing disarms both. The controller
reports changes as `RunStateChanged`.

### `EmulatorSession` methods (UI thread)

| Method | Effect |
|---|---|
| `freeze(owner)` | Stop the loop and mark frozen; on the emulation thread run to the next step boundary (`stepUntilNextKeycode`), `beginNextStep()`, then `frozenViewReady(Freeze)` |
| `freezeInPlace(owner)` | Mark frozen where the stopped machine stands (the ASM overlay's entry) |
| `resume()` | Unfreeze and start the loop |
| `clearFreeze()` | Unfreeze without starting (the caller stopped the loop to change state) |
| `armPcChange()`, `armScanLoopExit()`, `disarm…()` | The armed freezes; `FreezeController::checkStep` tests them per instruction in the run loop |
| `stepKeycode()` | While frozen: run to the next step boundary — one program byte, as SST; a jump completes in the byte that causes it — then `frozenViewReady(StepKeycode)` |
| `stepInstruction()` | While frozen: one `step()`, repeated up to 32 times while the PC stays put (a HOLD, `WAIT Dn`), then `frozenViewReady(StepInstruction)` |
| `setCpuPanelVisible(bool)` | The CPU panel needs the trace ring |

### Threading

- Freezes and steps are jobs on the emulation thread. The job queue is
  serial, so they run after the loop has exited.
- An armed freeze fires in the run loop. The session applies it (frozen,
  owner, new generation; for a CALCULATOR freeze also `beginNextStep()`) on
  the emulation thread **before** any listener runs, so the key sequencer
  never sees a stopped machine as running. Then
  `Listener::debugStateChanged()` and `frozenViewReady(generation, FreezeFired)`.
- `SessionController::onFrozenView` runs on the UI thread and builds the
  view only if the session is still frozen with the same generation. A
  RESUME or new freeze in between makes the event stale and it is dropped;
  so are events from a session replaced by a model switch.

### What a frozen view rebuilds

`DebugModel::frozenView(m, model, reason)` rebuilds the CPU history always,
and the CALCULATOR snapshot and listing for every reason except
`StepInstruction`. Showing the CALCULATOR panel while frozen rebuilds its
snapshot at once (`rebuildLive`).

The full listing is built only while frozen and reported with its own bit,
`ListingChanged`, so the 60 Hz running snapshot never carries the whole
program. It is never rebuilt from a `SolidStateReturn` snapshot (SCOM[0]
then holds a raw CROM address, not a step); the previous listing is kept.

### Frozen-display semantics

The CALCULATOR tab shows calculator-level boundaries only, running or
frozen, never the CPU mid-operation. `TMC0501::noteStepBoundary` latches
the CPU at each one (`lastStepBoundary()`), and `cu59::calcViewState` hands
the latest latch to `buildLiveSnapshot`:

- **Step boundary:** the next instruction is the interpreter's step dispatch
  (`0837` TI-59/58, `082B` TI-58C), once per executed program byte from RAM,
  a module or the constant-ROM keycode table. `step()` reports it with
  `kStepBoundary`; STEP and the armed CALCULATOR freeze stop on that bit.
- **Idle entry:** `0624` on every variant, where the ROM falls into the idle
  loop after a key operation or when a program stops (latched, no bit).

The position shown is **pre-execution**, as the LRN display shows it:
`currentStep` is the next step to execute, marked `← next` when frozen and
`← running` while running (`cu59::currentStepMarker`). Registers, flags, X
and T are the state before that step. `currentStep` comes from:

- **RAM programs and ROM keycode programs:** the SCOM[0] step counter. At a
  step boundary it names the byte about to execute. At idle entry it names
  the last one, so the next is counter + 1 — except after RST or a jump,
  which leave the target there with fB[11] (reload) set (`08B9`).
- **Solid State:** the library exec latch (`libExecPC`), the module byte
  fetched for dispatch. See `CoreArchitecture.md` § "How the emulator knows
  the current instruction".

The CPU tab is instruction-level and post-execution.

The frozen listing: `DebugModel::listing()`, `listingSource()`,
`listingCurrentIndex()` (Swift `programListing`, `programListingSource`,
`programListingCurrentIndex`; Qt `programListing()`,
`programListingSource()`). The view scrolls to the current entry.

## Live Debug Snapshot

`cu59::LiveDebugSnapshot` (`Shared/DebugSnapshots.hpp`) is the CALCULATOR
tab's data, built by `buildLiveSnapshot` from the latched boundary and held
by `DebugModel::live()`. It is rebuilt at 60 Hz while running and the panel
shows, and once per freeze or keycode step. The frontends compare with
`operator==` before redrawing. Swift copies it through `TILiveDebugSnapshot`
into `vm.liveDebugSnapshot` (a Swift struct with the same fields); Qt reads
`liveSnapshot()`. Text and colours both panels draw: `Shared/DebugText.hpp`.

| Field | Source | Meaning |
|---|---|---|
| `nonZeroRegs` | RAM | Non-zero data registers: `{num, value, isHidden}`; `isHidden` = TI-58C extra register H00–H03 |
| `programRegCount` | SCOM[9][0] | The claimed partition (not clamped to physical RAM) |
| `dataRegCount` | | Displayable data registers |
| `programWindow` | | `StepEntry` ±5 around `currentStep` (running view) |
| `currentStep` | | The next step to execute; −1 = unknown |
| `hir[0..7]` | SCOM[1..8] | HIR 1–8 |
| `tRegister` | SCOM[11] | T |
| `xValue`, `xRaw` | A or C, fA/fB | X, see below |
| `calcFlags[0..9]` | SCOM[0][11..15] | User flag N: nibble 11 + N % 5, bit 0 for N < 5, bit 1 otherwise |
| `fixIndicator` | SCOM[0][0] | `"-"` for 0, else (raw − 2) mod 10 |
| `statusRegister` | SCOM[0] | The whole status register (HIR 0), 16 hex digits, nibble 15 first; the DEBUG row shows it as `HIR0:` |
| `fA`, `fB` | | The flag registers |
| `invIndicator`, `secondIndicator` | fA bits 8, 9 | `"INV"`, `"2nd"` or empty |
| `engIndicator` | fB bit 7 | `"Eng"` or empty |
| `angleMode` | SCOM[13][0] | 0 = Deg, 1 = Grad, C = Rad, else unknown (C++ `optional<AngleMode>`; Swift `Int`, −1 unknown) |
| `prSourceFlag` | SCOM[0][3] | PRG SOURCE, raw |
| `programSource` | | `prSourceFlag` decoded with the CPU PC (`programSourceFrom`, `Shared/ModuleImage.hpp`) |
| `pendingOpsCount` | SCOM[13][0] | Provisional: the raw nibble (exact bits not established) |
| `scomRows` | SCOM | 16 rows as lowercase hex, nibble 0 first |
| `returnAddresses`, `returnAddressSourceFlags` | SCOM[14..15] | Return stack L1–L6 (below) |

`StepEntry`: `stepNum`, `keycode`, `mnemonic` (an operand step shows its
number), `isCurrent`.

### Program source

PRG SOURCE values and how the firmware tests them: `CoreArchitecture.md`
§ "PRG SOURCE flag". The listing's keycodes by `ProgramSource`:

| `ProgramSource` | Steps from |
|---|---|
| `UserProgram`, `FastMode` | Program RAM (`programSteps`) |
| `Rom` | The 384 constant-ROM keycodes (`romKeycodes`) |
| `SolidState` | The running module program (`ModuleImage::libraryStep`), steps program-relative |
| `SolidStateReturn` | None; the previous listing is kept |

Solid-state display details: `SharedArchitecture.md` § "Solid-State Program
Display".

### X

X is decoded from the latched CPU (`decodeX` in `Shared/DebugSnapshots.cpp`;
number formats: `rom/TI59-ROM-Guide.md`):

- A result on display (fB[5] set): C, normalized (nibble 0 = 0xC), signs in
  fB[2]/fB[3].
- Otherwise A, signs in fA[2]/fA[3]. Normalized at the first step of a
  keycode sub-program such as P→R. Else the entry image of a number being
  typed (digits 15–3, exponent 2–1, digits after the point in 0); at idle
  shifted back two places while B's exponent field is set (ROM `0662`; at
  the step dispatch the ROM has already done so at `07C1`).

When the register holds no number (mid-calculation, LRN mode, fast mode),
`xRaw` is `"C=…"` or `"A=…"` (nibble 15 first) and the line is amber. Both
panels show X with all 13 digits, before T.

### Return address stack

SCOM[15][0] counts the active levels (0–6). Each level is five nibbles:
PRG SOURCE, then a Base-80 address.

| Level | Nibbles |
|---|---|
| L1, L2, L3 | SCOM[15][1..5], [6..10], [11..15] |
| L4, L5, L6 | SCOM[14][1..5], [6..10], [11..15] |

`address = n[5]×800 + n[4]×80 + n[3]×8 + n[2]` for a level at nibble 1,
the same encoding as the SCOM[0] step counter. A library level holds a CROM
address instead. Colour by source (`returnLevelColor`): green RAM (0),
purple module (1, and 2 = saved CROM return address), yellow ROM (8), grey
otherwise; dimmer when the address is 0.

## CPU Inspector

One list, `DebugModel::cpuHistory()`, serves both states:

- **Running** (CPU panel visible): the newest 32 instructions,
  `recentInstructions(readTraceRing(m))`, the last one current; rebuilt in
  the 60 Hz frame only when the ring's newest `seqno` changed.
- **Frozen:** `inspectorHistory(m)` on every freeze and step — every frame
  still in the trace ring (read, not drained, up to 1024), then the next
  instruction (`isHistory = false`, zeroed frame), shown even at the same
  PC (WAIT and KEY loops re-execute one instruction).

```cpp
struct InspectorEntry {        // Shared/DebugSnapshots.hpp
    uint16_t pc;
    uint16_t opcode;
    std::string disasm;
    CpuFrame frame;   // state after the instruction (zeroed for the next one)
    bool isHistory;   // executed; false for the next instruction
    bool isCurrent;   // the last executed instruction
};
```

Swift receives `TIInspectorEntry` (frame as `TICpuFrame`, `Bridge/TITypes.h`)
and copies it into `vm.cpuHistory`; `vm.cpuHistoryUpdateID` changes with
it, so `CPUInspectorView` scrolls to the current entry. The ROM heatmap
(`DebugModel::heatmapCounts()`, `Shared/RomHeatmap`; Swift `vm.romHitCount`)
is fed from the same ring reads, while the CPU panel shows or the machine
is frozen.

### CpuFrame fields

`CpuFrame` (`Core/TraceTypes.hpp`) holds one instruction's CPU state. Every
frame the ring emits is **post-execution**: COND is finalized after the
jump-chain auto-restore, then written into the previous frame with the rest
of the state.

| Group | Captured with | Fields |
|---|---|---|
| Identity | always | `seqno` (gaps = ring overflow), `pc`, `opcode` (13 bits), `digit`, `postDigit`, `cycleWeight` (1 active, 4 idle) |
| Light | `TRACE_REGS_LIGHT` | `KR`, `SR`, `fA`, `fB`, `cpuFlags` (bit 0 IDLE, bit 11 COND), `R5` |
| Full | `TRACE_REGS_FULL` | `A`–`E` (16 nibbles, index 0 = least significant), `SCOM[16][16]`, `Sout[16]`, `EXT`, `PREG`, `flags`, `m_libAddr`, `REG_ADDR`, `RAM_ADDR`, `RAM_OP`, `m_libAddrReadPos`, `displayOn`, `maxDigitDecay` |

### Trace flags

`TI59Machine::setTraceFlags` (`Core/TraceTypes.hpp`). In the apps only
`EmulatorSession` sets them, from `traceFlagsFor(TraceConsumers)`: any
consumer (CPU panel visible, frozen, an armed freeze, manual or scripted
trace) gives `TRACE_PC | TRACE_REGS_FULL`; none gives `TRACE_NONE`, the fast
path.

| Flag | Cost | Records |
|---|---|---|
| `TRACE_PC` | Low | Identity fields |
| `TRACE_REGS_LIGHT` | Medium | + light registers |
| `TRACE_REGS_FULL` | High | + full snapshot |
| `TRACE_BREAKPOINTS` | Low | Breakpoint check per step (headless tools only) |

### Breakpoints

Core breakpoints (`TI59Machine::addBreakpoint`, `TRACE_BREAKPOINTS`,
`kBreakpointHit`) are used only by the headless tools (`tools/headless/`).
Neither app sets them.

### Disassembler

`static std::string TI59Machine::disassemble(uint16_t pc, uint16_t opcode)`
needs no machine state and returns a mnemonic such as `"ADD A, C [MANT]"`
or `"BR 0x03A2"`.

## LOG tab

The LOG is a `RingLog` (`Shared/DebugLog.hpp`, 2000 lines) held by
`DebugModel` and kept across model switches. `SessionController` writes the
dumps into it and refreshes `logText()` at 1 Hz (Swift `vm.debugDisplayText`,
Qt `logText()`).

| `SessionController` | Swift | Output |
|---|---|---|
| `dumpVars()` | `debugDumpVars()` | Non-zero data registers of the partition, sorted: `V05 = 2.5`, TI-58C extras as `H01` |
| `dumpScom()` | `debugDumpSCOM()` | 16 rows, nibble 15 first: `S00 0000000000000000` |
| `dumpProg()` | `debugDumpProg()` | Non-zero program registers as their 8 keycodes in step order: `P000: 76 11 …` |
| `dumpMemory()` | `debugDumpMemory()` | Every non-zero RAM register by physical index, in the `ti58c.mem` register-line format |
| `dumpStepCounterAnalysis()` | `debugDumpStepCounterAnalysis()` | SCOM[0], [10], [13] for step-counter study; no button in either app |
| `cycleDebugLevel()`, `clearLog()` | `toggleDebug()`, `clearDebug()` | Level Off → Info → Debug → Off; clear |

Qt has the same names as `SessionController` for the four dumps. The level
is passed to the core (`TI59Machine::setDebugLevel`). Shared code logs
through `SessionController` (or `EmulatorSession::Listener::logLine`).

### Core debug events

`TMC0501::emitDebug(level, fmt, …)` queues a `DebugEvent` (80-character
message, `vsnprintf` truncates) and is a no-op above the current level, so
it costs nothing when the LOG is off. `FrameSampler::tick` drains the queue
every 60 Hz frame (`TI59Machine::drainDebugEvents`), keeps events at or
below the level, and the controller appends them to the LOG.

| Level | Shown at | Use for |
|---|---|---|
| 1 (INFO) | Info, Debug | Infrequent events such as mode changes |
| 2 (DEBUG) | Debug | Per-instruction events such as register writes |

`emitDebug` is private to `TMC0501`; `TI59Machine` needs a public helper or
a call through `m_cpu`. `fmtNibs(d, buf, reverse)` in `TMC0501.cpp` formats
16 nibbles (`reverse = true`: nibble 15 first). Current DEBUG events:

| Message | Trigger |
|---|---|
| `STO SCOM[NN] = …` | SCOM write (STO / STOF / STOG), nibble 15 first |
| `MEMWR RAM[NNN] = …` | RAM write (MEMWR or RAM_OP), nibble 0 first |
| `RAM_OP CLR1 RAM[NNN]` | RAM_OP clear-1 (op 2) |
| `RAM_OP CLR10 RAM[NNN]` | RAM_OP clear-10 (op 4) |

## ASM Overlay

Runs hand-assembled TMC0501 code from a debug-only ROM region, for
ROM-level experiments. Core: `TI59Machine::loadDebugOverlay`,
`clearDebugOverlay`, `runDebugOverlay`. Shared: `cu59::parseAsmWords` and
`runAsmOverlay` (`Shared/AsmOverlay.hpp`), driven by
`SessionController::loadAsm`, `runAsm`, `clearAsm`.

**Address range.** `0x1800–0x1FFF` (2048 words), outside the normal ROM.
Words are masked to 13 bits.

**File format.** Examples from Hynek Sladký's *Calculators TI-58/59 HW
Programming Guide* are in `examples/assembly/` (its `README.md` has the
details).

```
PROGRAM:
; listing for people, ignored by the loader
1800:   01D8    MOV     A.ALL,#0
        ...

HEX:
01D8 01DB 0D00 0A37 1805 1007
```

Parsing starts after the `HEX:` line. Tokens are `0x…` or runs of 4 or more
hex digits, split into 4-digit words; everything else is skipped. A token
whose length isn't a multiple of 4, no `HEX:` line, no words, or more than
2048 words is a load error.

**Run.** The session stops, both armed freezes are disarmed and the
machine runs to the next keycode boundary. The overlay is loaded, COND is
set, and `PREG = EXT = 0x1800` is forced on every step — as the hardware's
external debugger does — until the computed jump lands on `0x1800`
(`TMC0501::runDebugInjectedProgram`). Not reaching it within 8192 steps
is an error ("ASM entry failed"); reset, then Run again. If the CPU's
FREEZE ON START was armed, the machine freezes in place at the entry
(`freezeInPlace(FreezeOwner::Cpu)`); otherwise the loop resumes and runs
the overlay in real time. An overlay
that loops forever runs until reset; one that ends with `0x0C00` (HOLD)
hands control back to the ROM.

**Persistence.** One overlay is shared across models: it survives reset and
is re-injected on a model switch, or dropped if it doesn't fit there.
`clearAsm` resets the machine if the overlay was running.

## Trace File Format

Files `CALCU59_TRACE.bin`, `CALCU58_TRACE.bin`, `CALCU58C_TRACE.bin`
(manual trace; scripted `Trace:` files take their own name). Written by
`Shared/TraceWriter`, read by `tools/read_trace.py`. Each open starts a
fresh file and session. All multi-byte fields are little-endian.

**Versions.** v1 (released in 1.0.0) is stable. v2 is the current writer
and may change between v2 revisions; readers should accept both.

```
[file header, 16 bytes]
[record: type u8, payload_length u16, payload]
...
```

### File header

| Offset | Size | v1 | v2 |
|---|---|---|---|
| 0 | 4 | magic `0x54493539` ('TI59') | same |
| 4 | 2 | version 1 | version 2 |
| 6 | 2 | reserved | model: 0 TI-59, 1 TI-58, 2 TI-58C |
| 8 | 8 | reserved | reserved |

### Records

Unknown types are skipped.

| Type | Name | Payload |
|---|---|---|
| 0x01 | SESSION_START | u64 Unix time (s); v2 adds u8 model |
| 0x02 | TRACE_EVENT | One `CpuFrame`: 125 bytes (v2), 124 (v1) |
| 0x03 | SESSION_END | u32 TRACE_EVENT count; u32 suppressed total, always 0 |
| 0x04 | USER_EVENT | u8 kind, u8 p1, u8 p2, u8 reserved |
| 0x05 | TRACE_GAP | u32 frames lost to ring overflow |

USER_EVENT kinds: 0x01 key down, 0x02 key up (p1 = row 1–9, p2 = col
1–5), 0x03 card insert, 0x04 card eject.

### TRACE_EVENT payload (v2, 125 bytes)

Post-execution state of one instruction.

| Offset | Size | Field |
|---|---|---|
| 0 | u32 | suppressed (always 0) |
| 4 | u32 | seqno |
| 8 | u16 | pc |
| 10 | u16 | opcode (13 bits) |
| 12 | u16 | fA |
| 14 | u16 | fB |
| 16 | u16 | KR |
| 18 | u16 | SR |
| 20 | u16 | EXT |
| 22 | u16 | PREG |
| 24 | u16 | cpu_flags (bit 0 IDLE, bit 11 COND) |
| 26 | u16 | m_libAddr |
| 28 | u8 | R5 |
| 29 | u8 | digit |
| 30 | u8 | RAM_ADDR |
| 31 | u8 | RAM_OP |
| 32 | u8 | REG_ADDR |
| 33 | u8 | m_libAddrReadPos |
| 34 | u8 | cycle_weight (1 active, 4 idle) |
| 35 | u8 | displayOn |
| 36 | u8 | maxDigitDecay |
| 37 | 5 × 16 | A, B, C, D, E: one nibble per byte, index 0 = least significant |
| 117 | 8 | Sout, packed: low nibble = Sout[2i], high = Sout[2i+1] |

v1 (124 bytes) has one byte at offset 35, `dispFilter` (0–3, ≥ 3 = display
blanked), and the registers from offset 36; `read_trace.py` derives
`displayOn` from it.

**Ring overflow.** The core's trace ring holds 1024 frames. When the drain
falls behind, a TRACE_GAP record gives the count lost, and `seqno` jumps by
the same amount.

## TI-58C Constant Memory File (`ti58c.mem`)

`SessionController` reads it when a TI-58C starts and writes it when RAM or
the user's cue card changed (`Shared/ConstantMemory`), through
`Platform::readConstantMemory` / `writeConstantMemory`; each app chooses
the location. When it is written: `SharedArchitecture.md`.

```
CUECARD:
Template: CueCard
Title: …

── Registers (raw values) ──
R000: 67 11 96 00 10 00 00 96
R063: 24 00 79 10 21 19 00 00
```

- The `CUECARD:` block is optional (grammar: `StateFileFormat.md`
  § "CUECARD: Field Grammar"); it ends at the `──` line.
- One line per non-zero register, `Rnnn` = physical index 000–119, eight
  hex bytes (`Shared/Bcd.hpp` `registerLineHex`). Missing registers are
  zero.
- A malformed register line makes the whole file invalid; RAM then starts
  zeroed.
