# Adding a New GUI Frontend

> **Provenance notice.** This document was generated by an AI (Claude) by
> reading the existing Swift/ObjC++ frontend and the WASM/JS frontend side by
> side, and by analyzing the `docs/#play` web port's own commit as a worked
> example of what porting the emulator to a new UI technology actually
> requires. It is a synthesis, not a spec handed down in advance — treat it
> the same way as the other `reference/*.md` files: best-effort, correct as
> of when it was written, and worth re-checking against source when it
> matters.

**This document is for anyone — human developer or AI agent — adding a new
GUI frontend for a platform Calc-U-59 doesn't yet support** (Windows, Linux,
Android, a second web build, etc.). It doesn't teach TI-59 hardware or AOS
arithmetic (see `reference/CoreArchitecture.md` for that); it answers a
narrower question: *given the existing Swift/iOS/Mac app and the
`docs/#play` web build as the two prior examples, what does a third GUI
actually need to implement, what can it reuse as-is, and what will it have to
reimplement from scratch because no shared, portable form exists yet?*

Two GUIs already exist and are worth reading as precedent before writing a
third:

| GUI | Language / UI framework | Binding to Core |
|---|---|---|
| Mac / iOS app (`App/`) | Swift + SwiftUI | `Bridge/TI59MachineWrapper.{h,mm}` — full surface (debug/trace/printer/card included) |
| Web (`docs/#play`) | JS + React (Babel-in-browser) + WASM | `docs/wasm/bindings.cpp` — narrow surface (no debug/trace/printer) |

Both bind the same `Core/TI59Machine` (see `reference/CoreArchitecture.md`).
Neither binding has business logic beyond type translation — that's a
deliberate property worth preserving in a third binding.

## The Contract a New GUI Must Implement

Each row below is one subsystem a new GUI needs, with a pointer to where it's
documented (or, where it isn't documented anywhere yet, a note to that
effect — several of these were undocumented until this pass; see the
sections and appendix below).

| Subsystem | Where it's documented | Notes |
|---|---|---|
| Core emulation API | `reference/CoreArchitecture.md`, `Core/TI59Machine.hpp` | Portable C++, no Foundation/ObjC dependency — usable as-is from any language with a C++ (or C-shaped) binding story. |
| A thin per-platform binding layer | `Bridge/TI59MachineWrapper.{h,mm}` and `docs/wasm/bindings.cpp` as two worked examples | Bind only what your GUI's feature set needs — the web build's narrow Embind surface (card reader bound, debug/trace/printer deliberately left out) is as valid a precedent as the Bridge's full surface. |
| Real-time run-loop pacing | `reference/AppArchitecture.md` → "Emulation Loop and Timing"; `docs/calc-engine-worker.js`'s `tick()` as a second worked implementation | Target 14,218.75 instructions/sec, cycle-weighted (IDLE steps cost 4× an active step), overshoot carried to the next tick rather than reset. Get this wrong and IDLE-heavy periods (e.g. the error blink) run at the wrong relative speed even though busy computation looks fine. |
| Key input coordinate mapping | `reference/AppArchitecture.md` → "Key Input Coordinate Systems" | Visual grid → matrix code (`row×10 + col`) → K-line bit. The matrix code table itself is also in `reference/StateFileFormat.md`, since state files use the same codes. |
| `.ti59`/`.ti58`/`.ti58c` state-file format | `reference/StateFileFormat.md` | Full section grammar (PARTITION/PROGRAM/REGISTERS/KEYSTROKES/CUECARD/etc.), including the CUECARD field grammar and math-token table. |
| LED display rendering | `reference/AppArchitecture.md` → "LED Display Rendering"; `docs/led-display.jsx` as a second worked implementation (SwiftUI `Canvas` → HTML `<canvas>` 2D, same bitmask table and shear/glow technique) | **Don't reach for an off-the-shelf 7-segment font.** The web build originally did, for everything except the "C" annunciator and digit 7 (special-cased as hand-drawn CSS bars because the font's glyphs didn't match) — `docs/led-display.jsx`'s header comment has the specifics: the font's "7" glyph lit a 4th segment real hardware doesn't, and its Latin "C" glyph was ~56% the height of a digit glyph, confirmed by decoding the font's `glyf` table. Every character (digits, minus, degree, blank, the C indicator) should be drawn from the same 7-segment bitmask table instead, exactly as `LEDDisplayView.swift` does — there is no font, general-purpose or otherwise, that reproduces real 7-segment hardware's actual lit-segment patterns for every glyph. |
| Cue-card look & feel (rendering) | `reference/AppArchitecture.md` → "Cue Card Rendering" | Per-template colors/dividers/layout, the `\blank` column-span-merge algorithm, and the shrink-to-fit font rule — previously existed only as unannotated SwiftUI layout code. |
| Card reader flow | `reference/AppArchitecture.md` → "Card Reader Flow" | The auto-eject-on-`CRD_OFF` polling pattern; `docs/calc-engine-worker.js`'s card-reader section is a second worked implementation of the same protocol. |
| ROM / module / constants loading | `reference/AppArchitecture.md` → "ROM Loading"; `tools/pack_roms.py` for the web build's binary-packed variant | Two different source formats for the same underlying ROM data — plaintext `.txt` (app) vs. packed base64 JSON (web) — both re-runnable from the same `roms/*.txt` sources. |
| Debug / trace / printer API (optional) | `reference/DebugAPI.md` | Only needed if your GUI exposes a debugger or printer UI — the web build deliberately doesn't. |

## Known Duplication Traps

Everything above the Core/binding-layer split in the table is currently
implemented exactly once per GUI, by hand, with no shared code and (until
this pass) largely no shared documentation either. Concretely, comparing the
Swift app and the web build:

- The run-loop pacing algorithm (constants and carry-over logic) is
  implemented independently in `EmulatorViewModel.swift` and
  `calc-engine-worker.js`.
- The cue-card math-token table (`\lambda` → `λ`, `^{2}` → `²`, etc., ~70
  entries) is hand-copied between `CueCardContent.swift` and
  `docs/cuecard-data.js`, with the JS copy's own comment admitting it must be
  "regenerated from the Swift source if it changes" — i.e., there is no
  automated sync.
- The `.ti59` state-file parser exists once in Swift
  (`StateFileLoader.swift`) and once in JS (`docs/state-file-parser.js`),
  ported by hand.
- The cue-card renderer exists once in SwiftUI (`CueCardView.swift`) and once
  in React (`docs/cuecard.jsx`), again ported by hand — `cuecard.jsx`'s own
  header comment says it was built by reading "`CueCardView.swift`'s actual
  field usage — NOT a re-imagining."
- The LED 7-segment display renderer exists once in SwiftUI `Canvas`
  (`LEDDisplayView.swift`) and once in HTML `Canvas` 2D (`docs/led-display.jsx`)
  — same bitmask table, per-digit shear, and two-pass glow technique,
  reimplemented by hand in the second API. Notably, the web build's *first*
  attempt didn't do this — it used a font for the digits and only discovered
  the bitmask-table approach was necessary after the font mismatched two
  specific glyphs (see the table above).
- The key row/col matrix table exists once in `TI59MachineWrapper.mm`
  (`kbits[]`) and once in `docs/matrix-keys.js`.

None of this is a defect in either existing GUI — each is a reasonable,
working implementation. But it means a third GUI faces the same choice the
web build faced: reimplement each of these by reading the *other* platform's
source, with no portable reference implementation to build against. The
documentation gaps above have now been closed; the code duplication has not.
See the appendix below for what to do about that.

## Appendix: Future Work — Reducing the Duplication

This is a set of candidates worth addressing before a *third* GUI has to redo
this porting work a second time, not a decision about how. Three shapes are
possible for each item, and nothing below should be read as picking one:

1. **Move it into `Core/`** — e.g. as a new `TI59Machine` method
   (`stepRealtime(dt)` encapsulating the pacing algorithm) or a static data
   table exposed alongside the existing API. Pro: every binding gets it for
   free, in the same language as the hardware simulation. Con: pulls
   UI-adjacent policy (timing pacing, cue-card text formatting) into a file
   that's otherwise pure hardware emulation — `Core/TI59Machine` currently has
   no Foundation/UI framework dependency at all (confirmed when the web port
   compiled it unmodified to WASM), and that boundary is worth keeping clean
   deliberately rather than by accident.
2. **A portable C++ helper alongside, but outside, `Core/`** — a new shared
   library (e.g. `Shared/` or similar) that depends on `Core/` but isn't part
   of it, compiled into both the ObjC++ Bridge and the Emscripten build the
   same way `Core/` already is. Pro: keeps `Core/` itself hardware-only while
   still sharing real code (not just a spec) across every C++-embeddable
   binding. Con: doesn't help a GUI written in a language that can't easily
   embed C++ (this repo's two GUIs both can; a hypothetical native
   Windows/Linux GUI written in, say, C# or a JVM language might not).
3. **A single-source, language-neutral data table generated into each
   platform** — e.g. the math-token table as one JSON/CSV file, with a small
   generator script producing the Swift array and the JS array (and whatever
   a third platform needs) from it, so there's one edit location and a CI or
   build-time check that the generated copies match. This is the lightest
   fix and the best fit for pieces that are pure data (the math-token table,
   the key-matrix table) rather than logic (the run-loop pacing algorithm,
   the state-file parser).

Candidates, roughly in order of how cheaply they'd fit approach (3) above
before needing (1) or (2):

| Item | Nature | Best-fit approach (tentative) |
|---|---|---|
| Cue-card math-token table | Pure data (string→string) | (3) — single generated table |
| Key row/col matrix table | Pure data | (3) — single generated table |
| Run-loop pacing (target Hz, IDLE weighting, carry-over) | Algorithm, ~10 lines, no UI dependency | (1) or (2) — could live in `Core/` as a `stepRealtime`-style method, since it only touches `step()`'s return value and a clock |
| `.ti59` state-file parser | Algorithm + format, no UI dependency | (2) — a shared C++ parser would remove an entire hand-ported file per new GUI, at the cost of every GUI needing to embed it |
| 7-segment bitmask table (digits, minus, degree, blank, "C" annunciator) | Pure data | (3) — single generated table; the shear/glow *drawing* logic underneath it is still platform-specific `Canvas` code either way, same caveat as the cue-card renderer row below |
| Cue-card renderer (visual layout) | Rendering logic tied to each platform's UI framework | Not a good fit for any of the three — SwiftUI/React/a future native toolkit can't share render code. The fix here is keeping `reference/AppArchitecture.md`'s "Cue Card Rendering" section (added alongside this doc) current as new templates or fields are added, so the *rules* stay documented even though the code can't be shared. |

Whoever builds the third GUI is well positioned to judge this concretely —
by the time state-file parsing and cue-card rendering are ported a second
time (the first being this document's own source material, the web build),
the actual cost of each duplication will be obvious in a way it isn't from
design discussion alone.
