# Shared C++ Layer (`Shared/`)

> **Provenance notice.** This document was generated by an AI (Claude) while
> moving the Swift app's non-GUI logic into `Shared/` and building the Qt6
> app on it. Like the other `reference/*.md` files it is best-effort and
> correct as of writing — the code wins where they disagree.

`Shared/` holds everything the frontends need that is neither hardware
emulation nor drawing. It sits between `Core/` (the emulated hardware, see
`CoreArchitecture.md`) and the three GUIs — the two apps and the web client
(`WebClient.md`):

```
App/ (SwiftUI) ── Bridge/ (ObjC++) ─────────┐
Qt6/app/ (Qt Widgets) ──────────────────────┼── Shared/ (C++17, std only) ── Core/
Web/ (React) ── Web/bindings.cpp ───────────┘   (WebAssembly, no threads)
```

- **C++17, standard library only** — no Foundation, no Qt, no iCloud. The
  root `CMakeLists.txt` builds it as C++17 (the Xcode project compiles it as
  gnu++17), so a C++20-ism fails the CMake build.
- **No locations.** `Shared/` never resolves where files live: it takes paths
  (`std::filesystem::path`) or a `ResourceReader` callback that returns a
  bundled file's text by name (Swift: `Bundle.main`; Qt: the `:/roms/` qrc).
- **Thread-safe where called across threads** (session, runner, sequencer,
  trace writer, freeze controller); the rest is plain value code.
- **Namespace `cu59`.** Headers include Core relatively (`../Core/...`).

The Qt app calls `Shared/` directly. The Swift app goes through the ObjC++
wrappers in `Bridge/`, which only translate types (`AppArchitecture.md`
§ "Bridge Layer").

## `SessionController`

Each app owns one `SessionController` on its UI thread and is otherwise a
renderer: the Qt app through `EmulatorController`, the Swift app through
`EmulatorViewModel` and `Bridge/TISessionController`. The controller owns the
`EmulatorSession` (rebuilt on a model switch) and the `DebugModel`, and runs
the flows both apps share: starting and switching machines, presets, the
TI-58C memory file, the card reader, the printer strip, the cue card shown,
freeze and step, traces, the ASM overlay and the LOG tab.

The app implements `SessionController::Platform`: `runOnUiThread`, reading
and writing `ti58c.mem` and card files, the trace location (and whether it
is available, asked only when a manual trace opens), saving the last model
and module, error alerts, diagnostics, and `changed(mask)` — the `Change`
bits name what to redraw. The app calls `tick(now)` at 60 Hz, and
`suspend()` / `resumeAfterSuspend()` when it goes to the background.

Session events hop to the UI thread through `Platform::runOnUiThread` and
are dropped there if their session has since been replaced (each session
has a generation) or the controller is gone.

### The 60 Hz tick

One `tick(now)`:

1. **Frame** (`FrameSampler`): each position's glyph and brightness
   (`DisplayPov`), the C indicator's smoothed opacity, printer text and dot
   lines, core log lines, and card auto-eject (the core executed `CRD_OFF`;
   written data is saved).
2. **Debugger** (`DebugModel::tick`): the CALCULATOR snapshot while its panel
   shows; the CPU history and heatmap while the CPU panel shows.
3. **Traces**: the core's trace ring drained into the open writers.
4. **Slower checks**: the cue card's library program (2 Hz), the LOG text
   (1 Hz), the TI-58C persist (0.5 s after a batch ran).

`changed()` then names only what actually changed.

## Threads

| Thread | What runs there |
|---|---|
| Frontend UI thread | `SessionController`: `tick()`, every user action, arming freezes; drawing |
| Emulation thread (`EmulationRunner`, one per session) | The paced run loop, and every job posted with `post()` / `sync()` — warm-up, freeze-to-keycode, steps, state application, ASM entry — always after the loop has exited |
| Key sequencer lanes (`KeySequencer`) | KEYSTROKES playback and physical-keyboard taps: two independent lanes, so a key press never cancels a script |
| Key sequencer timer | Deferred releases (a key let go before its 100 ms minimum hold) |

`EmulatorSession::Listener` callbacks arrive on the emulation or sequencer
threads; `SessionController` hops them to the UI thread.

### Cooperative mode (no threads)

`Threading::Cooperative` (`Shared/Threading.hpp`, the last argument of
`SessionController`, `EmulatorSession`, `EmulationRunner` and `KeySequencer`)
runs all of the above on the frontend's UI thread instead. The web client
uses it — a static host can't be relied on to allow threads (no
`SharedArrayBuffer` without COOP/COEP headers) — and so do the tests on virtual time
(`tests/shared_cooperative_tests.cpp`). The apps use `Threading::Threads`.

- `SessionController::tick(now)` first calls `EmulatorSession::pump(now)`.
- `EmulationRunner::pump` runs the 20 ms batches due by `now` on the same
  absolute schedule as the thread (a lag over 100 ms restarts it); at full
  speed it runs batches back to back for at most 10 ms of wall clock. Jobs
  queued behind a stopped loop run at the end of the pump; `sync()` runs the
  queue, then the job, inline.
- `KeySequencer` scripts and taps are resumable tasks in both modes — the
  same state machine, which says when it next wants to run. Threaded, each
  lane's thread sleeps until then; cooperatively, the session advances the
  lanes after every batch, at the time that batch ends, so a 100 ms hold is
  five batches and the scan-loop wait is checked at each batch boundary.

`sync()` waits for the job; call `stop()` first, or it waits for the run
loop. Key playback reads the session's frozen state, so it stops waiting for
an idle CPU that will never come.

The session owns the debugger's freeze state and the core's trace flags.
Freeze, step and their threading: `DebugAPI.md` § "Freeze / Step Controls".
Core locking: `CoreArchitecture.md` § "Threading Model".

## Emulation Loop and Timing

`EmulationRunner` runs `Pacing::runBatch` in a loop:

1. Call `step()` and add up the returned cycle weights until they reach the
   batch target: the model's instruction rate × 20 ms (14,218.75 Hz → 284 on
   the TI-59; 12,000 Hz → 240 on the TI-58; 12,312.5 Hz → 246 on the TI-58C).
   The overshoot carries into
   the next batch, so the long-term rate stays exact. Each batch ends at a
   random offset of 0 to half a batch past its grid point (`BatchJitter`:
   batch n runs target + rₙ − rₙ₋₁, so the offsets never accumulate). The
   frontends sample the CPU between batches; with fixed batches a ROM loop
   whose length divides the target is caught at the same instruction every
   frame — the TI-58's 80-step error-blink dark pass in 240 froze the CPU panel
   (`cooperative_runner_batch_ends_do_not_lock_onto_a_loop`).
2. Sleep until the batch's deadline. Deadlines are absolute, each 20 ms after
   the previous, so oversleep is paid back in the next batch. A lag over
   100 ms, or a batch that doesn't sleep, restarts the schedule. Timing
   each batch from a fresh `now()` instead runs about 17 % slow on macOS
   (`runner_keeps_real_time` in `tests/shared_runtime_tests.cpp`).
3. Full speed skips the sleep, except while the PC is in the model's
   scan/key-detect range or the batch polled hardware (`shouldSleep`).

`step()` returns the cycle weight in the low 8 bits (`kWeightMask`). Bit 29
marks a step boundary (the CALCULATOR freeze stops on it). Bit 30 marks a confirmed
hardware poll (a key or card-switch wait; not a printer BUSY wait, which is
counted in emulated cycles, so full speed speeds up printing). Bit 31 marks
a breakpoint: core breakpoints are set only by the headless tools, and the
loop just stops. An armed freeze that fires stops the batch, and the session
applies it before reporting it.

## Key Input Coordinate Systems

| Layer | Coordinates |
|---|---|
| Frontend hit test (`KeyboardLayout`) | Visual row 0–8, col 0–4 from the top left |
| `matrixCode(row, col)` (`KeyMatrix`) | `(row+1)×10 + (col+1)`, 11–95 — the codes KEYSTROKES uses |
| `pressMatrix` (`KeyMatrix`) | `code / 10` → digit slot, `code % 10` → column → K-line bit via `kKBits` |
| `TI59Machine::pressKey(kbit, digitSlot)` | `key[digitSlot] \|= 1 << kbit` in the CPU |

`kKBits` maps column 1–5 to K-line bits `{1, 2, 3, 5, 6}` (index 0 unused);
bit 4 is the card-detect line. Scanning: `CoreArchitecture.md`
§ "Keyboard Matrix and Scanning".

## Physical Keyboard Mapping

Computer keyboards drive the calculator in the macOS Swift app, the Qt6 app
and the web client (`Web/`, with its `keyboard` prop). iOS/iPadOS and the
web client's standalone app (`Web/app/`) have no keyboard input. The debugger and printer panels take no calculator
keys: Space (R/S vs. STEP) and Cmd/Ctrl+C (printer tape vs. selected text)
would have no single owner.

Values below are matrix codes. The website's keyboard legend
(`TI59_KEYBOARD_LEGEND` in `calc-u-site`'s `59/Pages.jsx`, prerendered without the engine)
lists the same bindings by hand.

### What is bound

**26 of the 45 keys, deliberately**: the white (digit) keys, the yellow keys
except 2nd, A–E, and EE / `(` / `)`. 2nd, INV, lnx, CE, LRN, x⇄t, x², √x, 1/x,
SST, STO, RCL, SUM, yˣ, BST, GTO, SBR, RST and R/S are pointer-only on
purpose. Do not "complete" the table without asking. With 2nd unbound, the
only second functions a keyboard reaches are A′–E′.

### Rules

1. A binding resolves to one or two matrix codes. 2nd functions are reached
   as on hardware: 2nd, then the key.
2. Shift + letter means "2nd, then that letter's key". Only `a`–`e` and
   `x` (×) are bound, so this gives A′–E′ and, with `x`, Deg.
3. Non-letters resolve on the character the keyboard produced, so Shift is
   not a 2nd prefix for them: `Shift+.` is `>` → EE. Lookup goes by produced
   character, never by scan code, so non-US layouts work wherever they put
   these characters.
4. With Command, Control or Option/Alt held, no key is the calculator's.

### The table

| Keyboard | TI key | Matrix | | Keyboard | TI key | Matrix |
|---|---|---|---|---|---|---|
| `0`–`9` | 0–9 | 92 82 83 84 72 73 74 62 63 64 | | `Escape` | CLR | 25 |
| `.` `,` | . | 93 | | `/` | ÷ | 55 |
| `<` | +/− | 94 | | `*` `x` | × | 65 |
| `a`–`e` | A–E | 11–15 | | `-` | − | 75 |
| `A`–`E` (Shift) | A′–E′ | 21 + 11–15 | | `+` | + | 85 |
| `>` | EE | 52 | | `=` `Return`/`Enter` | = | 95 |
| `(` `)` | ( ) | 53 54 | | | | |

Numeric-keypad keys produce the same characters and need no entries. `x` is
× as well as `*`, so a keyboard without a numpad needs no Shift for
multiplication.

### Injection timing

`key[]` is a wire level, not an event; the ROM accepts a key only when two
scans one display sweep apart see it, and drops a shorter press as bounce
(`ideas/KeypressLatch.md`). Every frontend uses `KeySequencer`:

- A press is held at least 100 ms. A key-up that comes sooner defers the
  release; it is never dropped. The web client sends on-screen clicks
  this way too, so a click shorter than that still registers.
- A tap waits for the steady scan loop before it presses, and again after it
  releases, so a key never lands in the ROM's release gate or debounce.
- One key at a time: a key-down while another is held releases the first.
- OS auto-repeat is ignored. A held key can never re-trigger, so repeats
  would only cause spurious releases.
- A two-code binding is one action played as two full taps; its key-up is
  ignored, because the ROM must see 2nd released and rescanned first.
- Losing focus releases the held key.

### Focus

Keys reach the calculator only while it has focus. It takes focus at launch
and on every click on the calculator. There is no focus indicator, so
clicking into the debug panel silently stops keys reaching the calculator.
This is a stepping stone: the Mac is meant to end up with one input surface
where every key has one meaning (`TODO.md` § UI). Panels that need keys
themselves (the CPU inspector's arrow keys) take focus on click, never on
appear. The web client is focusable (`tabIndex=0`, focused on
pointer-down with `preventScroll`) but not focused on load, so Tab still
works on the page.

## Card Reader Flow

The core side (TST BUSY wait, `CRD_READ`/`CRD_WRITE`, auto-eject at
`CRD_OFF`) is in `CoreArchitecture.md` § "Magnetic Card Reader". The
controller's side:

1. `insertCard(bytes, path, name)` decodes the file (`CardFile`), takes its
   cue card if it is a text card, and calls `machine.insertCard`.
   `insertBlankCard(savePath, name)` inserts an empty card for writing.
2. The card state is `Swiping` until the core auto-ejects.
3. `tick()` sees the auto-eject and calls `ejectCard()`, which collects any
   written bank and saves it, with the current cue card, through
   `Platform::writeCard`.

Presets feed cards through the same insert path (`ArmCard:` / `InsertCard:`,
§ "State File Loading"); `Platform::cardFile(name)` resolves a card file name
in the frontend's card folder.

Card files are written as text ("Calc-U-59 Card 1.0", `Shared/CardFile.hpp`).
Still read: the 13-byte `Calc-U-59-CRD` header + 246 bytes, and headerless
246- or 984-byte files.

## State File Loading

`SessionController::loadStateFile` writes the file's state straight into
RAM; only `KEYSTROKES:` simulates key presses. Section semantics and the
reference order: `StateFileFormat.md`.

1. UTF-8 check; `prescanStateFile` (`MODEL:`, `SKIP-RESET:`); `parseStateFile`
   with the target model's limits. Parse errors are reported and the load
   continues.
2. `MODEL:` names another model → `startMachine(target)` first. Then the
   partition check (`stateFilePartitionError`) aborts either path below.
3. With `SKIP-RESET:`: stop the loop, unfreeze, and on the emulation thread
   write only the partition (if explicit), program and registers
   (`applySkipResetState`). The ignored `MODEL:`, `SOLID-STATE-MODULE:` and
   `PRINTER:` are logged to the LOG tab.
4. Otherwise: stop the loop,
   unfreeze, and on the emulation thread `applyState` (`StateApplier`):
   reset, run the ROM's power-on routine (300,000 steps, a safe upper bound),
   set the partition, clear RAM (the TI-58C keeps registers 60–63), write the
   program zero-padded to the model's capacity, write the registers. Then
   reset the heatmap baseline, start the loop and cut the paper, and apply
   `SOLID-STATE-MODULE:`, `PRINTER:` and the cue card.
   A full load first drops the previous preset's queued and memory cards
   (`dropPresetCards`).
5. Persist `ti58c.mem`, then play `KEYSTROKES:`.

**Reloads and preset cards during playback** (`StateFileFormat.md` §
"Reloads", § "CARD"). The parser puts each reload stage and `CARD:` block
into the keystroke events (`shared_ptr`). This is the order of operations:

1. A `Reload` or `InsertCard` event waits for the scan loop like a key. It
   then calls a `KeySequencer::Host` hook (`EmulatorSession`), which raises
   the session's host-pending count.
2. The sequencer waits until that count drops.
3. A reload hops to the UI thread (`Listener::reloadRequested`). There
   `SessionController::applyReloadStage` stops the loop, runs `applyReload`
   on the emulation thread, restarts the loop (unless frozen), and updates
   the cue card. It then calls `hostDone()`. A posted job would not do: it
   runs only after the run loop exits.
4. `ArmCard` and `InsertCard` queue their card in the session (`QueuedCard`,
   under a mutex).
5. On each 60 Hz `tick()` with an empty reader, `takeQueuedCard()` hands out
   the front card:
   - an `InsertCard` card when the PC is in the scan loop;
   - an `ArmCard` card when the PC is in `ModelInfo::cardWait` and the core
     reports a card wait.
6. `feedQueuedCard` resolves the card:
   - a `mem:` card from its written bank, its `CARD:` block
     (`buildCardBank`, at the current partition), or blank;
   - a file through `Platform::cardFile`.

   It inserts the card as the card picker would. On eject, a written bank
   goes to the memory card or to the file, and an `InsertCard` calls
   `hostDone()`.
7. `playbackFinished` clears the pending count. Queued cards stay until the
   next full load, reset or model switch.

Skipping the power-on routine leaves stale SCOM flags that confuse the
display and AOS.

## TI-58C Constant Memory

The TI-58C keeps its RAM through power-off. `SessionController` saves the
whole RAM and the user's cue card as `ti58c.mem` (`ConstantMemory`; format
in `DebugAPI.md`) through the platform, which decides where the file lives.

| When | What |
|---|---|
| Machine start | Power-on routine, then the saved RAM restored (`powerOn`), so startup code can't overwrite it |
| 0.5 s after a run-loop batch | Rewritten if its contents changed |
| Model switch, preset load, `suspend()` | Written at once if changed |
| Reset | Reset, then the saved RAM restored (`softReset`) |
| Clean reset | RAM zeroed, reset, written at once |

## ROM Loading

`RomLoader` parses the text dumps in `roms/` (header, a `---` line, then
`AAAA: WWWW …` rows, words masked to 13 bits) through the frontend's
`ResourceReader`. `MachineModelInfo` names each model's files: three ROM
chips concatenated into 6144 words and two `*-CONST-K.txt` files for the 64
constant rows.

| Model | ROM chips | Constants |
|---|---|---|
| TI-59 / TI-58 | `TMC0582.txt`, `TMC0583.txt`, `TMC0571B.txt` | `TMC0582-CONST-K.txt`, `TMC0583-CONST-K.txt` |
| TI-58C | `CD2400.txt`, `CD2401.txt`, `TMC0573.txt` | `CD2400-CONST-K.txt`, `CD2401-CONST-K.txt` |

The TI-59 image is checked against two sentinels: word 0 = `0x0A01`
(`CLR IDL`) and word 6143 = `0x1987`. Solid State modules are
`roms/solid-state/TMC05xx.txt`, named by `MODULE-ROM` in `cuecards.txt`.

## Drawing Rules

Both apps draw with the same shapes and numbers; only the painting calls
differ.

### LED Display Rendering

- Glyphs: `SevenSegment` (`ledCell(i, digit, ctrl, level, calcOpacity)`:
  segments and opacity per cell, the "C" annunciator in cell 11), never a
  font. Zero suppression happens in the core (`TMC0501`), which reports
  suppressed positions as not driven; `ledCell` blanks a position at
  level 0. All three renderers call it.
- Shapes: `LedGeometry` — hexagonal segments (modernized) or dot grids
  (classic), the decimal point, and per style the slant (bottom fixed; shear
  0.14, about 8°, modernized; 0.1139, about 6.5°, classic), colours and glow radii. The decimal point is not
  sheared.
- Brightness: `LedFrame` gives 0–255 per digit and decimal point
  (`DisplayPov`).
- Each frontend paints a blurred glow (and, modernized, a tighter bloom)
  under the crisp segments.

### Cue Card Rendering

Field grammar: `StateFileFormat.md` § "CUECARD: Field Grammar".

- **Templates.** `CueCard`, `MagnetCard` and `SolidStateCard`, each with its
  own artwork (`App/Assets.xcassets`) and fractional layout
  (`cueCardLayout`). Only `SolidStateCard` has an ID and column dividers, and
  is printed gold (`0xC49223`); the others use the card's ink (black, pencil,
  sharpie). Only `MagnetCard` has bank badges.
- **Which card shows** (`resolveCueCard`): the running library program's
  card, else a generic card for the module, else the user's card (card file,
  preset, `ti58c.mem`).
- **Column spans** (`labelSpans`, `dividersBetween`). A grid row has 5
  cells. A `\blank` cell extends the preceding label's span; empty cells
  draw nothing.
- **Shrink-to-fit** (`cellFittingFontSize`). Each grid row gets one font
  size, the largest at which every span fits on one line (bold character
  width 0.64 × size), never below 40 % of the template's size. Free-text
  rows truncate instead.

The web client gets the card as a draw list `Web/bindings.cpp` builds with
these functions for the size the page reports, and paints it on a canvas
(`Web/src/painters.js`), badges included.

### Printer

`PrinterFont` holds the PC-100C 5×7 font and the paper geometry measured
from a real unit: dot pitch ≈ 0.430 mm, line heights including lines cut
short, and the copy-as-image scale (600 dpi, capped for long strips).
`PrinterGeometry::lineDots` turns a line cut short by the printer interrupt
(Core's `PrinterCodeLine`) into the dot rows drawn and, per row, the inked
and faint columns; `inkAlpha(heat)` gives a faint dot's ink (full from 20
heating cycles), `lineHeightUnits` the line's height on the strip. All three
renderers draw from these.

## Solid-State Program Display

The CALCULATOR tab's program view resolves where the running program comes
from with `programSourceFrom` (`ModuleImage`), which decodes the PRG SOURCE
flag as the firmware does (`CoreArchitecture.md` § "PRG SOURCE flag") plus
the CPU PC: bit 0 → `SolidState`; else bit 3 → `Rom`; 0 → `UserProgram`;
2 with the PC inside the RTN → LIB_RETURN window (ROM 1193–1194, 14F9–1506)
→ `SolidStateReturn`; any other 2, 4 or 6 → `FastMode`.

- `ModuleImage::parse` reads the module header into program ranges;
  `DebugModel` re-parses it when the machine or module changes.
- `ModuleImage::libraryStep()` maps the core's latched `libExecPC` (`0xFFFF`
  = none) to program, program-relative step (000 = the program's first
  keycode) and range. The program is cross-checked against SCOM[9] digits
  4/3 (mismatches go to the diagnostics).
- During `SolidStateReturn`, SCOM[0] nibbles 4–7 hold a raw CROM address,
  not a step. A listing is never built from it; the previous one is kept
  (`DebugModel::rebuildLive`).
- Colours: solid-state steps highlight blue; return levels with source 2
  show purple, like library levels (`DebugText`).

Snapshot fields and freeze semantics: `DebugAPI.md`.

## Tests and goldens

`tests/` (CTest target `CalcU59Tests`, run from the repo root) covers the
modules, with the ROMs from `roms/` (`LedGeometry` has no test of its own;
`BatchJitter` is covered through the cooperative runner). A second target,
`CalcU59TraceReader`, runs `tools/read_trace.py` on the trace the tests wrote
(`build/trace-test.bin`), so the reader stays in step with `TraceWriter`. Ports of Swift code are checked against
goldens produced by compiling the Swift original (`tools/goldens/`,
`tests/golden/`).
